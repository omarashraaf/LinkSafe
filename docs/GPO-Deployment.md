# Domain GPO Deployment

This deploys the client for each domain user on each targeted Windows x64 workstation. It installs/enables the agent and requests the initial backup without a setup window. Existing users receive the new folder selection once too. It is a **user logon deployment**, not an MSI assignment and not a SYSTEM startup script.

## Safety And Scope

- The application is still a trusted-LAN MVP with unverified client API identities. Pilot on controlled workstations; do not confuse GPO distribution with backend authentication hardening. Do not expose the API to untrusted networks.
- Defaults are Desktop, Documents, Downloads, Pictures, Videos, Music, Favorites, AppData Roaming and Chrome/Edge/Firefox profiles, plus ready **fixed local drives except C:** and the actual Windows system drive if different. User folders on C: are still backed up. USB/removable, network, CD/DVD and unavailable/locked drives are not automatically selected.
- Selection is a one-time local override. Later user changes and pauses are preserved on GPO reruns. Global exclusions/protected paths/size limits still apply. Each user can only read files their normal account can access; do not grant extra access to scan another user's protected files.
- Whole additional drives can contain shared/confidential data and consume substantial storage for every user. Limit the GPO to intended workstation users, exclude privileged/server accounts, and verify capacity. Do not link indiscriminately to domain controllers, servers or multi-session/RDS hosts.
- A pre-existing Stop backup signal remains paused and is reported in the log. The deployment enables the agent but does not erase that pause or restore data automatically. Initial worker launch skips the interactive restore offer; later normal logons retain normal restore consent behavior.
- The initial backup runs in the background. Offline users retry when the service/network returns; installation success is not proof of upload success. No mechanism can install/run for a user who is not logged in or a PC that is off.

## 1. Prepare The Package

Build on a Windows signing/build machine with PowerShell 7.3+, not each client. Distribution builds require an existing code-signing certificate in the current user's Personal store (including access to its private key), a trusted certificate chain, and an approved Authenticode timestamp service. The builder never creates/imports certificates, exports keys, changes trust or submits binaries to antivirus vendors.

```powershell
pwsh -NoProfile -File Scripts/Build-LinkSafeGpoPackage.ps1 -SigningCertificateThumbprint "YOUR_40_HEX_CERTIFICATE_THUMBPRINT" -TimestampServer "YOUR_APPROVED_TIMESTAMP_URL"
```

Use a timestamp URL supplied by your signing provider, not the placeholder above. The builder signs both EXEs and the logon script with SHA-256, requires valid embedded signatures from the selected signer with timestamps, then hashes the final bytes. Any signing/verification failure stops publication. A valid signature establishes publisher/integrity, not antivirus approval or application safety.

Each successful build produces a **new** `artifacts/GpoDeployment/<build-id>` directory (the exact path is printed), leaving older local packages untouched. The directory contains:

```text
LinkSafeClientSetup.exe       unattended-capable setup 1.0.17+
LinkSafeClientAgent.exe       worker 1.0.16+
package.json                 SHA-256 checks for both binaries
Deploy-LinkSafeClientGpo.ps1  user logon script, Windows PowerShell 5.1 compatible
README.md                    this guide
```

It is a deployment directory, not a client ZIP download. Copy the complete directory to a **new versioned folder** on your software distribution server, for example `D:\LinkSafeSoftware\gpo-1.0.17`. Do not replace a package while clients are reading it. Do not place the EXEs in SYSVOL: they contain runtimes and are large.

For isolated development only, `pwsh -NoProfile -File Scripts/Build-LinkSafeGpoPackage.ps1 -AllowUnsignedDevelopmentPackage` permits unsigned output and records `Signing.Mode=UnsignedDevelopmentOnly` in the manifest. Do not distribute that kit to domain users. Signing metadata in `package.json` is informational; the manifest is not itself an authenticated trust anchor. Share permissions and Windows signature verification remain essential. Rebuilding or changing a signed script invalidates its old signature: re-sign and verify the final distribution copy. Do not replace a reviewed signed package with an unsigned build.

Do not use the older EXE generated by the website for this workflow: that version does not understand `--gpo-install`. No .NET SDK/runtime install or compilation is required on workstations.

## 2. Create A Separate Read-Only Software Share

Using Server Manager / File and Storage Services, share the software directory as `LinkSafeDeploy$`, for example:

```text
\\BACKUP-SERVER\LinkSafeDeploy$\gpo-1.0.17
```

Grant the deployment user group **Read & Execute** in NTFS and **Read** on the share. Give write/full permissions only to trusted software deployment administrators and SYSTEM as appropriate. Users must not be able to modify the script, EXEs or manifest. Use normal domain SMB authentication; never put credentials in the script. Hash verification detects corruption, not a compromised writable share. Follow organizational code-signing and script execution policies; deployment does not bypass them. The server installer and website Downloads build path are separate and are not automatically signed by this GPO builder.

This share contains **software only**. Keep `D:\LinkSafeBackups` / `D:\UsersBackup` and their shares admin-only. Actual backups still upload to the HTTP API, never this software share. Restrict distribution/API/firewall access to the intended LAN.

## 3. Create And Scope The GPO

1. Open Group Policy Management (`gpmc.msc`) as a domain administrator on the management machine.
2. Create `LinkSafe - User Agent Deployment`. Start with a pilot security group and an OU containing test users. Do not deploy to the entire domain before the pilot passes.
3. Edit **User Configuration > Policies > Windows Settings > Scripts (Logon/Logoff) > Logon > PowerShell Scripts**.
4. Use **Show Files**, copy only `Deploy-LinkSafeClientGpo.ps1` into that GPO's script folder, then add it on the PowerShell Scripts tab.
5. Enter the parameters below, replacing the sample server IP/share with your actual values. Do not include `powershell.exe`, `-ExecutionPolicy Bypass`, an administrator password, or SYSTEM credentials.
6. Keep logon processing asynchronous so the desktop need not wait for package copying or backups. Do not enable visible scripts. The child setup/agent are hidden, and the normal client tray is started.
7. If immediate logon execution is required, configure **Computer Configuration > Policies > Administrative Templates > System > Group Policy > Configure Logon Script Delay = Disabled** in an appropriately scoped computer GPO. Windows can otherwise delay logon scripts.

Example script parameters (the application accepts only the IP in `ServerIp`):

```text
-PackagePath "\\BACKUP-SERVER\LinkSafeDeploy$\gpo-1.0.17" -ServerIp "10.0.0.10" -Port 5055 -DeploymentId "default-folders-fixed-drives-v1" -MaxStartDelaySeconds 180
```

Security filtering must grant the intended user group **Read + Apply Group Policy**. Preserve the computer accounts' required read access to user GPOs (for example Domain Computers Read in Delegation, not Apply). Verify OU/security/WMI filters with `gpresult`; do not remove required GPO read permissions blindly. User policy linked only to a computer OU does not automatically apply to user objects; use the correct user OU or have IT explicitly design loopback processing.

Microsoft references: [user logon script configuration](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2012-r2-and-2012/dn789196(v=ws.11)), [logon script delay](https://learn.microsoft.com/en-us/troubleshoot/windows-client/group-policy/logon-scripts-not-run-for-long-time), [Group Policy processing](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/group-policy/group-policy-processing).

## 4. Pilot And Roll Out

On test PCs, sign in as a normal targeted domain user. `gpupdate /target:user /force` refreshes policy but is not a guarantee that a logon script runs immediately: sign out and back in. Default random startup delay is up to 180 seconds to reduce server/network spikes; use 0 only for a small pilot.

For an already logged-in test user, IT can run the same approved script manually in that user's **non-elevated** PowerShell to execute now. Do not start it remotely as SYSTEM or impersonate a different administrator. Existing supported workers/UIs can be reused without terminating them. An unmanaged, inaccessible or pre-1.0.16 installation can require a maintenance-window update; failures are logged, not hidden.

Verify all of these before expanding the security group/OU scope:

- Installed Apps / Start lists LinkSafe Client; tray is present. The worker runs as the intended user, not SYSTEM.
- Task Scheduler has `LinkSafe Client Agent (USER-SID)`, interactive/least-privilege, logon trigger and restart settings. Confirm another sign-out/in actually starts it.
- Client folder selection includes standard folders and the ready fixed non-C drives on that PC, not C: as a whole drive. Test two PCs with different drive layouts and a PC with no additional drives.
- Put a small approved test file in Documents and in an additional drive. Confirm actual bytes arrive in that user's/computer's server backup. Inspect real success/error reports; a deployment receipt or queued request is not success.
- Test an existing client, pre-existing pause, offline server, existing local selection, locked drive, multiple separate users on one PC and unavailable software share. No protected ACLs or another account's files should be changed.
- Run the logon deployment twice with the same ID: it must not reset later choices or requeue repeated forced initial backups.

When the pilot passes, expand to the intended domain user groups. They will install/apply at their next logon, not all simultaneously at the instant a GPO is linked. Do not mass-logoff users or force backups across the domain without a communicated rollout window.

## State, Retry And Removal

Bootstrap cache/log: `%LOCALAPPDATA%\LinkSafeDeploymentCache\deployment.log`.
Installer log: `%LOCALAPPDATA%\LinkSafeAgent\Logs\gpo-install.log`.
Agent log: `%LOCALAPPDATA%\LinkSafeAgent\Logs\backup-agent.log`.
Application receipt: `%LOCALAPPDATA%\LinkSafeAgent\gpo-deployment.json`.

The private cache avoids recopying unchanged large binaries. SHA-256 is checked before execution. Failed deployments are retried by the next logon; the success receipt is written only after startup has been requested successfully. Package/share outages do not disable an already installed agent.

The same deployment ID is applied once per Windows user profile/device. It replaces folder choices and enables once, not on every policy refresh. A different ID intentionally applies the baseline again, including current ready drives: use only for an approved policy reset. Drives attached later are not silently added; choose them in the agent or schedule a new baseline ID. A different server is never adopted silently; migrate explicitly. Keep the same ID during simple redistribution.

Removing/unlinking the GPO prevents future deployment; it does **not** uninstall or disable installed agents. Use the normal per-user uninstall process if required. Existing client/server config, logs, queue and backups are retained. The rollout does not erase or restore user files. It does not enforce tamper-proof installation against users who can edit their own profile state.

## Antivirus Detection And Signing

Stop a rollout if endpoint protection removes/quarantines the app. Do not repeatedly reinstall, rename/repack binaries to evade a detection, disable protection or add broad folder exclusions. Preserve the exact detection name/module, timestamp, path, file SHA-256, signature and versions for review. Do not assume a false positive solely because the source is yours or the file is signed.

Review the reported behavior against the source and clean build. LinkSafe intentionally copies installed binaries, registers per-user startup/Installed Apps, reads selected user/app folders and uploads backups; these permissions need organizational approval. There is also an encoded PowerShell cleanup command in the existing explicit uninstall path; it is not invoked by GPO installation, so its presence alone does not explain an install-time alert. Do not change runtime behavior based on guessed signatures.

Have IT distribute only the approved public trust chain and publisher certificates to the intended pilot accounts/computers, following [Microsoft's certificate GPO procedure](https://learn.microsoft.com/en-us/windows-server/identity/ad-cs/distribute-certificates-group-policy). Keep private keys on the signing machine/HSM, never in the deployment share or repository. An internally trusted certificate does not establish public publisher reputation. Under AllSigned, validate the final script's signature and publisher trust as the actual user; do not use an execution-policy override. Scope certificate and execution-policy changes carefully because they affect more than LinkSafe.

Submit suspected false positives through [Bitdefender's official review process](https://www.bitdefender.com/business/support/en/77211-343054-resolving-legitimate-applications-detected-as-threats-by-bitdefender.html). Obtain approval before uploading proprietary binaries; never submit backups, profiles, tokens or private keys. For oversized samples, follow Bitdefender's support instructions. A vendor verdict/updated detection and a clean controlled pilot are required before claiming the issue fixed. Signing alone does not guarantee acceptance.
